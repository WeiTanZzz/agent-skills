# Deck HTML

Goal: one self-contained `.html` file that passes the deck.txz.cool validator with 0 errors (and ideally 0 warnings),
fits a 1280×720 stage on every slide, and keeps the source's content and look.

## 1. Read the spec first

Read [references/spec.md](references/spec.md) in full before planning. It is the source of
truth (format, forbidden constructs, reserved ids, theme tokens, conversion checklist); if anything here disagrees
with it, follow the spec. Its minimal example is the best starting skeleton. `references/spec.md` and
`scripts/validate.js` are generated by the deck platform; never edit them here.

## 2. Understand the source

- **HTML page or deck**: read the whole file plus its local CSS and assets. List every `<script>`, `on…` attribute,
  `<link>`, external URL, `<iframe>`/`<form>`/embed, and any `vw`/`vh` or JS-driven scaling: each one needs a decision.
- **Markdown, notes, outline, PDF text**: find the audience, the main sections, and what is backup material.
- Ask only when an answer would change the result (audience, length, what is presenter-only); otherwise decide and
  state the assumption in the report.

## 3. Plan the slides

Write the plan as a list before any HTML: `id · data-title · data-parent · home/private`.

- Ids: lowercase kebab-case, meaningful and stable (`pricing`, not `s3`). Never a reserved id; `next`, `map`,
  `progress`, `live` and `bar` are tempting slide names that are reserved.
- If there is an index/agenda, it gets `data-home` and links to sections with `data-go`. Detail slides get
  `data-parent` = the slide they drill down from.
- Backup/appendix slides: `data-private`. Speaker notes: a `data-private` element on the public slide.
- One idea per slide. If content does not fit 1280×720 at a readable size (body ≥ 15px), split the slide; never rely
  on scrolling.

## 4. Write the file

Save next to the source (`pitch.html` → `pitch.deck.html`, `talk.md` → `talk.deck.html`) or where the user says.
Never modify the user's source file.

**Converting behaviour** (no scripts allowed; re-express, don't drop silently):

| Source behaviour | Deck HTML v1 |
|---|---|
| Link/button that jumps to a slide | `data-go="<id>"` on the element (prefer `<button>`) |
| Show/hide, accordion, "read more" | `<button data-toggle="k">` + `data-toggle-target="k"` + your own CSS: target hidden, `.open` shown |
| Confetti or other click celebration | `data-fx="burst"` on the toggle trigger (only on a `data-toggle` element) |
| Tab switcher (one panel at a time) | No radio behaviour exists. Prefer one slide per tab: repeat the heading and tab bar on each, mark the current tab, link tabs with `data-go`. Or show the panels side by side if they fit, or use independent toggles. Say which you chose |
| `alert()` / "thanks" message on click | A toggle that reveals the message (add `data-fx="burst"` if it was celebratory) |
| Smooth-scroll to a section | `data-go` to that section's slide |
| Prev/next, progress bar, page numbers, slide menu, keyboard handlers, fullscreen | Delete: the runtime provides them |
| Live charts, `fetch`, timers, counters, custom JS widgets, forms, video embeds | Bake into static HTML/inline SVG/a `data:` image (forms → a static mock, embeds → a still + an `https` link). List each one in the report as "made static" |

Toggles are independent and global: state survives slide changes and syncs to viewers. Style the trigger's
`[aria-expanded="true"]` for "Hide …" labels. Up to 16 keys; every key needs a trigger and a target.

The runtime writes class `active` on the current slide and `open` on toggle targets. Rename the source's own state
classes (`.tab.active` → `.tab.current`) and drop generic `.active { … }` / `.open { … }` rules, which would also hit
slides and targets.

**Assets**

- Images/audio/video only as `data:` URIs. One file: `printf 'data:image/png;base64,%s' "$(base64 -i logo.png | tr -d '\n')"`.
  Many local files: write the deck with their relative paths, then run
  `bun <this-skill-dir>/scripts/inline-assets.ts <deck.html> [--base <source dir>]` (rewrites in place,
  drops non-`data:` `srcset`, reports remote/missing files and the final size).
- Remote images (`https://…`): ask the user before downloading; otherwise replace with inline SVG or a styled
  placeholder and say so.
- Size limit 5 MB, and base64 adds ~33%. Shrink photos on macOS:
  `sips -Z 1600 -s format jpeg -s formatOptions 75 in.png --out small.jpg`. Prefer inline SVG for diagrams and logos.
- Fonts: only Google Fonts (`<link rel="preconnect">` + `<link rel="stylesheet" href="https://fonts.googleapis.com/css2?…">`)
  or `@font-face` with a `data:` src. Replace Typekit, Bunny, self-hosted and other font links with the closest Google
  Font (re-check line wraps: metrics differ) and mention it. Delete favicons, preloads and every other `<link>`; move
  external CSS into `<style>`.

**Layout and design**

- Lay out for exactly 1280×720 (slide padding included). Convert `vw`/`vh` to px at 1vw = 12.8px, 1vh = 7.2px, and
  rewrite source rules on bare `section`/`body` (e.g. `min-height: 100vh`) since slides are sections. No
  `transform: scale` on the stage, no positioning of slides.
- Never set `display` on `.slide`; use `.slide.active { display: flex; flex-direction: column }`, and for one slide's
  layout `.hero.active { flex-direction: row }`.
- Theme with the spec's tokens in `:root` (`--paper`, `--ink`, `--accent`, `--letterbox`, …) and use them in your own CSS
  so the runtime chrome (status bar, slide map, cursor) matches.
- When converting, keep the source's visual design: colours, fonts, spacing and components. Restructure only what the
  spec forces.
- Put speaker notes in an absolutely positioned box (e.g. bottom-right) so removing them for viewers doesn't shift the
  public layout; the presenter's cursor and selection are mirrored to viewers in stage coordinates.
- Close every element explicitly inside `data-private` content (the server parser applies no implied end tags).

## 5. Validate and fix

```sh
bun <this-skill-dir>/scripts/validate.js deck.html
```

Add `--json` for structured output; exit code 1 means errors. Each message names the element and its slide
(`<button> in #intro: data-go="pricng" is not a slide id`) and a rule from the table at the end of the spec. Fix and re-run until ✓, then fix warnings unless the user disagrees.

The validator can't see layout. Check fit with the preview script, which stacks every slide as a dashed 1280×720
frame (anything crossing a frame doesn't fit; private elements get an amber outline):

```sh
bun <this-skill-dir>/scripts/preview.ts /absolute/path/deck.html          # as the presenter sees it
bun <this-skill-dir>/scripts/preview.ts /absolute/path/deck.html --open   # every toggle open
bun <this-skill-dir>/scripts/preview.ts /absolute/path/deck.html --viewer # private content removed
```

It prints the path of a CSS-only HTML file (no scripts, so a static snapshot renders it too). Screenshot it with a
browser tool if one is available (viewport ≥ 1300px wide, scroll to each `#id` label); otherwise give the user the
path to open. Fix overflow by splitting slides or tightening layout, not by shrinking text below ~14px.

## 6. Report

Tell the user, briefly:

- The output path, slide count and the validator's final line.
- The slide plan (ids, home, parents, private slides/notes) and anything made static, replaced or dropped, with why.
- How to publish: open `https://deck.txz.cool/admin` → drop the file (the admin runs the same validation) → pick a slug
  (lowercase letters, digits and `-`; not a reserved name like `admin`, `api` or `runtime`) → set a viewer password and a
  presenter password (required for a new deck) → share `https://deck.txz.cool/<slug>` with the viewer password and
  sign in with the presenter password to present. Re-uploading to the same slug replaces the deck, keeps the
  passwords and reloads open copies.

Do not upload, deploy or download anything yourself unless the user asks.

## Most-missed rules

- `<meta name="deck:spec" content="1">` and a `<title>`; slides are top-level `<section class="slide" id data-title>`
  (not `<div>`, not nested).
- Toggle targets need your own hidden-by-default CSS and an `.open` rule, or the toggle does nothing visible. A public
  trigger needs at least one public target (all targets `data-private` is an error); private triggers may open public
  targets.
- `data-go` goes on a `<button>` or an `<a href="#id">` (keyboard-reachable); an `<a href="#x">` naming no slide or
  element id is a warning.
- No `<script>` (JSON-LD included), no `on…` attributes, no `javascript:` URLs, no `<iframe>`/`<form>`/`<object>`.
- Every `src` is `data:image|audio|video/…`; CSS `url()` is `data:` or `#fragment`; `@import` only Google Fonts.
- Ids are unique document-wide, including SVG `<defs>`/marker/gradient ids in repeated diagrams.
- No public `data-go`, `<a href="#id">` or `data-parent` may point at a private slide; the home slide is public.
